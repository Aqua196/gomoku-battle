# REVIEW_M4 — gomoku-battle M4 阶段独立评审

基点：`origin/main` @ `9086d91`（相对 `m3-done` tag）。评审人：独立评审 agent（只读）。
验证：`go test -race ./...` 全绿（含 miniredis contract 20.8s）；`docker compose config` 语法有效；在 /tmp 副本跑 3 个 miniredis FastForward 探针（rooms set 泄漏/TTL 滑动/宕机创建）全部实证。

**一句话结论**：Docker/CI 骨架可用，但 RedisStore 有三类真实问题——**所有 Redis 网络 IO 都在 `h.mu` 持锁内执行**（Redis 抖动=全枢纽冻结）、**降级路径把瞬时故障放大成永久数据分叉**（miss 即新会话/创建假成功）、**TTL 语义与 MemStore 不等价且集合泄漏**（`rooms` 集合尸体实测确认）。CI 从不构建镜像也不跑容器关卡。

---

## major

### M4-R1 全部 Redis IO 在 `h.mu` 持锁内执行 — Redis 延迟/重试直接冻结整个枢纽
- **位置**：`handlers.go:75`（`PlayerByToken`）、`:90`（`UpdateNick`）、`:104`（`CreatePlayer`）、`:158/:389/:397`（`UpsertRoom`）、`:39/:225/:429`（`DeleteRoom`）——均在 `Hello`/`newRoomLocked`/`gameOver`/`PlayerDisconnected`/`JoinRoom` 的 `h.mu` 临界区内；`hub.go:163`（sweep 的 `DeletePlayer`，同样锁内）。
- **问题**：Store 接口被当内存用，但 RedisStore 每次调用是 1~N 个网络 RTT（`context.Background()` 无超时上限，go-redis 断线时还有 dial 重试）。实测探针 C：Redis 关闭时一次 `put` 烧 **~3.3s 重试**——这把秒的 hub 全局停顿摊在每次 hello/建房/断线清理上；Redis 慢查询（负载/网络分区）期间 lobby 与所有对局信令（含 AI、重连、sweep）全部停摆。
- **触发**：`REDIS_ADDR` 指向不可达/慢 Redis（compose 里 redis 容器重启即复现）。
- **修复**：store 调用移出锁外（先查内存态、锁外持久化、锁内仅登记内存态）；或给 RedisStore 加 `context.WithTimeout`（如 200ms）+ 写操作异步化（写穿队列）；`slog.Warn` 之外加指标计数以便发现。

### M4-R2 降级语义把瞬时 Redis 故障放大成永久会话/对局丢失
- **位置**：`redis.go:70-99`（一切错误→`nil,false`）、`:46-67`（`CreatePlayer` 写失败仍返回非 nil rec）；契约测试 `store_test.go:122-143` 把「宕机即 miss」固化成规范。
- **问题**：(a) `PlayerByToken` 在 Redis 抖动时 miss → `Hello` 把它当未知 token → 发新会话——**旧对局对这名玩家永久不可达**（内存里 h.players 仍有他，但入口被封）；(b) `CreatePlayer` 在写失败时仍返回 rec（实测探针 C：`redis down` 下返回 `p_3rj8…`/43 字符 token）——hub 认为会话已持久，重启/重连后蒸无此人；(c) 「graceful fallback」只在启动时发生一次（`main.go:26-34`），运行期 Redis 故障没有任何自愈/告警升级——只会刷 warn。
- **修复**：区分 miss 与 transport error（接口加 `ErrStoreUnavailable` 或对错误统一 `503/try_later` 回给客户端而不是静默发新身份）；`CreatePlayer` 失败应向上传导；运行期重连/自愈策略或明确文档声明"Redis 故障=会话全丢"。

### M4-R3 容器编排缺 healthcheck/启动条件 — RedisStore 启用依赖竞态运气
- **位置**：`docker-compose.yml:15-16` `depends_on: - redis`（仅启动顺序，无 `condition: service_healthy`）；redis 服务与 app 均无 `healthcheck`；`main.go:26-34` 仅启动时 Ping 一次。
- **问题**：compose up 时 app 与 redis 几乎同时启动，app 的 Ping 若先于 redis ready（~几百毫秒的窗口）→ 立即永久降级 MemStore——「带 Redis 的栈」静默跑成内存模式，直到下次重建才恢复。证据 `compose-up.txt` 里 `INFO store: redis` 是运气好而非确定性。
- **修复**：redis 加 `healthcheck: ["CMD","redis-cli","ping"]` + app `depends_on.condition: service_healthy`；或 NewRedisStore 做有限重试（~5s 退避）。

### M4-R4 TTL 语义与 MemStore 不等价：`rooms` 集合尸体泄漏实测确认 + 玩家 TTL 读不滑动
- **位置**：`redis.go:20-22`（`playerTTL=24h`, `roomTTL=1h`）、`:46-58`（仅 `put` 写时刷新 TTL）、`:128-134`（`SAdd rooms` 但 set 本身无 TTL）、`:161-174`（`ListRooms` 遍历全部成员再逐个 GET）。
- **实证（探针）**：A) 5 个 room upsert 后 FastForward 2h → room key 全过期、`ListRooms`=0，但 `rooms` 集合仍含 5 个尸体 id ——**集合单调泄漏**，任何 ListRooms 都要 GET 一遍尸体（N+1）；B) 玩家 23h 时读 token（命中）→ 25h 仍被驱逐——**读不滑动 TTL**：一个在线>24h（且未改 nick）的玩家记录蒸发，断线后永远无法恢复会话；C) MemStore 无任何 TTL，contract 套件声称语义等价但这条差异完全没有被测出。
- **修复**：读路径 `EXPIRE` 续期（pipeline GET+EXPIRE）；`rooms` 集合改用按分数的 ZSET（score=expire ts）+ `ZREMRANGEBYSCORE` 定期清理，或 ListRooms 顺手 SRem 尸体；在 contract 套件加 TTL/恢复语义用例（miniredis `FastForward` 可用）。
