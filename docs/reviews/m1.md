## 问题清单（按严重度排序）

---

### R1 — [critical] 断线重连错过窗口/服务端重启后，前端被钉死在"幽灵棋盘"且无逃生路径

- **位置**：`frontend/src/state/store.tsx:120-130`（`welcome` reducer 不清 `game`/`lobby`）；`frontend/src/App.tsx:28-38`（`Redirector`：`inGame` 时强制回 `/game`）；`backend/internal/hub/handlers.go:105-117`（`ResumeGame` 仅在 `StatePlaying` 时发 `game_state`，无"无对局"信号）
- **描述**：`state.game.game` 一旦非空，`Redirector` 就把用户钉在 `/game`。清掉 `game` 的唯一途径是 `CLEAR_GAME`，而它只挂在"对局结束弹层"的返回按钮上。以下场景产生 stale game：
  1. 玩家断线超过 `RECONNECT_WINDOW` → 服务端判负、房间删除 → 重连后 `welcome(resumed=true)` 但**没有** `game_state`（房间已不存在）→ 旧 `game` 残留；
  2. 服务端重启（MemStore 全丢）→ `hello{旧token}` 走 fresh 分支 → `welcome(resumed=false)` → 同样无 `game_state`；
  3. 任何 token 失效场景同上。
- **触发条件/复现**：开局 → kill 对端连接超过重连窗口 → 重连。客户端收到 `welcome` 后无后续 `game_state`，`game.game` 保持断线前快照，`turnDeadline` 已过期被 clamp 成 0s，棋盘看似仍在对局。`/game` 页面对 playing 状态只有"认输"按钮 → `resign` 收到 `not_in_room` toast；手动输 URL `/` → `Redirector` 推回 `/game`。**会话内无 UI 逃生路径**，只能整页刷新（重载后内存态清空才能回大厅）。
- **修复建议**：(a) `welcome` reducer 中 `resumed=false` 时重置 `game`/`lobby` 为初始态；(b) `resumed=true` 时启动短定时器，若 ~1s 内无 `game_state` 则清 `game`（或协议加 `game_absent`/`lobby_state` 显式信号——改协议需先改 PROTOCOL.md）。

### R2 — [major] 快速重连/僵尸连接场景下 token resume 被拒为 `unauthorized`，客户端永不回退

- **位置**：`backend/internal/hub/handlers.go:76-79`（`p.conn != nil → EUnauthorized`）；`frontend/src/ws/client.ts:61`（每次 hello 都带 LS_TOKEN）；`frontend/src/state/store.tsx:241-244`；`frontend/src/App.tsx:18`（unauthorized → 普通 toast）
- **描述**：`hello{token}` 命中**仍在线**的会话 → `unauthorized`（防劫持，方向正确）。但服务端判"在线"依赖旧 conn 的存活视图：客户端网络静默切换（NAT 重绑、Wi-Fi 切换）时，服务端要等旧 conn 的 read error / pong 超时（最长 `WSPongWait=30s`）才发现其已死。这期间所有自动重连的 `hello{token}` 全部被 `unauthorized` 拒绝。前端对该错误无特判：不降级为无 token hello、不换提示、按指数退避原地重试 —— 大厅用户被锁在门外最长 ~1 分钟，且每轮都被 `hello_timeout` 关闭再重来，错误提示"会话失效，请重新进入"与实际行为（持续重试）矛盾。多开第二个 tab 同样永久被拒并刷错误。
- **触发条件/复现**：探针 P2 已验证 busy-token → `unauthorized`；P1 显式 close 立即重连 20/20 成功（说明仅在"服务端未及时察觉断线"的僵尸窗口内失败，恰是真实网络切换的主场景）。僵尸复现：客户端层丢包不 close（如拔线）→ 新 conn hello{token} → unauthorized 循环直到旧 conn pong 超时。
- **修复建议**：优先 **takeover**——`Hello` 里 `p.conn != nil` 时直接 `p.conn.Close()` 踢掉旧连接并绑定新连接（token 本就是凭证；协议未禁止顶替）；若坚持拒绝语义，则返回可区分错误码并让前端在 `unauthorized` 后清 token 走新会话（代价是丢对局席位，只适合大厅态）。

### R3 — [major] 房间列表全量广播风暴 → 正常客户端被误判慢消费踢出（自 DoS）

- **位置**：`backend/internal/hub/hub.go:177-188`（`broadcastRoomList` 全员全量）；`hub.go:139-141`（`Send` 满 → `Close`）；`backend/internal/integration/e2e_test.go:879-882`
- **描述**：任何 create/join/leave/disconnect/gameover 都向**所有非 playing 连接**推全量 `room_list`。N 个房间变化 × 每连接 SEND_BUF=64：突发 churn（批量建房、批量断线）瞬时产生 >64 帧的 backlog，正常浏览大厅的客户端被当慢消费者强制断开。仓内自己的 100 房压测就因此被迫"pace the pairings"（测试注释明说 200 个瞬时 matchmake 会打满 64 帧缓冲踢人）——即**已知会炸的规模点被绕过而非修复**。踢出还会让玩家在 playing 态意外断线、启动判负窗口。
- **触发条件/复现**：~70+ 并发建房/删房动作 vs 挂机大厅客户端 → 客户端连接被服务端关闭。e2e 注释即证据。
- **修复建议**：按连接合并广播——每 conn 置 dirty 位由 writePump 只发**最新一份** `room_list`；或发送时丢弃被更新的 room_list 覆盖（send channel 里已有未消费 room_list 则替换）；或 throttle 到固定频率（如 200ms/轮）。

### R4 — [major] 玩家/会话表只增不减，内存随访客数单调泄漏

- **位置**：`backend/internal/hub/handlers.go:94-98` + `17-54`；`backend/internal/hub/hub.go:82`；`backend/internal/store/memstore.go:27-36`
- **描述**：每个无 token hello 都 `CreatePlayer` 并永久挂入 `h.players` + `playersByID`/`playerIDByT`。`PlayerDisconnected` 只置 `conn=nil` 保留会话（断线恢复所需），但**不存在任何过期/淘汰路径**——大厅断线就走人的游客也永久驻留，token 永不过期。MemStore 同理无 `DeletePlayer`。公网部署下内存随独立访客线性增长，且被广播循环（`lobbyConnsLocked`/`roomListMsgLocked` 遍历 `h.players`）放大遍历成本。
- **触发条件/复现**：脚本循环 dial+hello+close（不带 token）→ `h.players`/`playersByID` 单调增长，无回���。
- **修复建议**：给断线会话加 TTL（如对局内会话保留 `RECONNECT_WINDOW`，非对局会话短 TTL），定时扫描淘汰；`Store` 接口补 `DeletePlayer`/`ExpireSessions`；M4 换 Redis 时用原生 expire。

### R5 — [major] Actor 无 panic 兜底且 `onOver` 非 defer：一次意外 panic 永久卡死房间与两名玩家

- **位置**：`backend/internal/game/actor.go:101-146`（`run()`；`onOver` 在 145 行**不在** defer 中）
- **描述**：`run()` 的唯一退出路径是 `status != playing` → `onOver` 删房并归还玩家到大厅。任何 panic（applyMove/sendGameStart/未来改动引入的 nil deref 等）会让 `run()` 直接退出：defer 只 `close(done)`，**`onOver` 被跳过** → `h.rooms` 残留 status=playing 的房间、两位玩家锁死在 `StatePlaying`（`create_room`/`join_room`/`matchmake` 全被 `already_in_room`/`not_in_lobby` 拒绝，`resign`/`move` 投给已死 actor 被吞）且无日志无告警。评审中未发现现存可达 panic 路径，但容器化前没有任何故障隔离就是埋雷。
- **触发条件/复现**：向 actor 任意处理路径注入 panic（如未来 AI/新消息类型），房间即不可回收，直到进程重启。
- **修复建议**：`defer` 内统一收尾：`defer func(){ if r:=recover(); r!=nil { log... }; close(done); a.onOver(a.roomID) }()`——房间与玩家状态无论如何都被回收。

### R6 — [major] 计时器与 mailbox 的 select 竞先：按期到达的落子/重连可被超时判负（违反"先到先生效"）

- **位置**：`backend/internal/game/actor.go:111-119`（`select` 三分支）；`actor.go:267-290`（`onTurnTimeout`/`onReconTimeout` 用 `time.Now()` 而非事件到达时刻）
- **描述**：Go `select` 对多个就绪 case 随机选择。若某事件（move/reconnect）在 `t<D` 已入 mailbox，而 actor 正在处理上一事件跨过 `D`，则下一轮 select 中"已触发的 timer"与"排队中的按时事件"**同时就绪** → ~50% 概率选中 timer → `onTurnTimeout`/`onReconTimeout` 用 `time.Now()≥D` 判负，把 mailbox 里按时到达的动作整个丢弃。同理重连事件 vs `reconDeadline`。规范 §5/§4 意图是先到先生效，此实现边界判定是非确定性的。事件量小使窗口很窄（µs–ms 级），但属真实竞态，且正是本评审维度点名的"超时与重连窗口竞先"。
- **触发条件/复现**：deadline 前最后一刻连续发送多个事件（合法 move 在最后），使 drain 跨越 deadline；统计 game_over 出现 `timeout`/`disconnect_timeout` 而 move 未生效的概率（非 0）。
- **修复建议**：timer case 命中后先 `for { select { case f:=<-mailbox: f(); default: goto check } }` 排空已排队事件再判定；或给事件附到达时间戳，判定时用 `event.ts < deadline` 而非 `now`。

### R7 — [minor] 配对成功后仍回 `matchmaking{queued}` 陈旧帧

- **位置**：`backend/internal/hub/handlers.go:245-258`
- **描述**：第二个 matchmake 触发配对后，`position` 是配对前算的、`queue` 已出列，但代码仍无条件 `reply(queued, position)`。探针 P3 实测帧序：`queued{position:2}` → `game_start` —— 客户端瞬间先"入队"再"开局"，自相矛盾（前端 `lobby.matchmaking` 短暂置真）。
- **修复建议**：配对分支置标记，`actor != nil` 时跳过 queued 回复（或加 `matched` 状态——改协议需同步 PROTOCOL.md）。

### R8 — [minor] 建房/加入房间隐式出队不回 `matchmaking{cancelled}`，前端匹配态卡死

- **位置**：`backend/internal/hub/handlers.go:135`（CreateRoom）、`176`（JoinRoom）`dequeueLocked` 静默；`frontend/src/state/store.tsx:142-150`；`frontend/src/pages/Lobby.tsx:104-121`
- **描述**：玩家在队列中点建房/加入房间 → 服务端 `dequeueLocked` 移出队列但**不通知**；前端 `lobby.matchmaking` 保持 `true` → UI 持续显示"匹配中"并把创建/匹配/人机按钮全部 disabled，直到下一条 matchmaking 消息或手动点取消。用户视角是"按钮全灰但显示在匹配"。
- **修复建议**：隐式出队时补发 `matchmaking{cancelled}`（复用现有帧，零协议成本）。

### R9 — [minor] 对手断线状态固定绑在白方卡片：我执白时把断线标到自己头上

- **位置**：`frontend/src/pages/Game.tsx:73-87`（`online={oppOnline}` 只传给 white 的 PlayerCard）
- **描述**：`opp` 按 `youColor` 取反计算正确，但 `online` 属性只挂给 white 卡片：执黑时对手（白）断线 → 白卡显示"断线"✓；执白时对手（黑）断线 → **白卡（我自己）显示"断线"，黑卡恒"在线"**。横幅与 deadline 仍正确，卡片状态错位。
- **修复建议**：`online={color === oppColor ? oppOnline : true}`，或直接按 `player.connected`/`opponentOf` 逐个卡片绑定。

### R10 — [minor] 倒计时直接用客户端钟减服务端 deadline，时钟偏差全盘传导

- **位置**：`frontend/src/pages/Game.tsx:47-52`；`frontend/src/hooks/useNow.ts`
- **描述**：`turnLeft = turnDeadline − Date.now()`。两端独立时钟（本机/部署机/NTP 漂移）：客户端钟慢 → 服务端已判负而 UI 仍显示"你的回合 Xs"；客户端钟快 → 剩余时间被低估甚至直接 0。重连窗口同理。无偏差估计机制。
- **修复建议**：hello/pong 回包里带 `serverNow`，前端估 `offset = serverNow − Date.now()`（或用 ping RTT/2 修正）；或所有 deadline 以"剩余毫秒"下发。

### R11 — [minor] `conn.Send` 在 `quit` 已关后仍可入队：`select` 随机分支 → 丢帧但返回 true

- **位置**：`backend/internal/ws/conn.go:35-44`
- **描述**：`quit` closed 且 send 未满时，`case c.send<-data` 与 `case <-c.quit` 同��就绪，select 随机选——可能走 send 分支返回 `true`，但 writePump 已退出 drain 循环，帧永久滞留/丢失，调用方误以为已投递。影响限于"关闭中"的连接，属角落但语义不干净。
- **修复建议**：先 `select{case<-c.quit:return false;default:}` 再进三选 select（经典 double-check）。

### R12 — [minor] 错误码不一致：同在房间中，`matchmake` 回 `not_in_lobby`，`create/join` 回 `already_in_room`

- **位置**：`backend/internal/hub/handlers.go:236-239` vs `130-133`/`160-164`
- **描述**：同一前置条件（已在房间/对局中）三种入口两种错误码。客户端若要按码分桶（如 already_in_room → 提示先退房），matchmake 路径语义错位（玩家其实在房间里而非"不在大厅"）。另：`LeaveRoom` playing 分支先回 `room{left}` 再 `actor.Resign` → 认输方收到 `left` 先于 `game_over`（`handlers.go:216-219`），对端只见 `game_over`；协议未规定次序，客户端若按"left=已退出"语义处理会短暂矛盾。
- **修复建议**：统一为 `already_in_room`（语义更准确）；playing 中 `leave_room` 先走 resign，把 `room{left}` 与 `game_over` 合并或由 game_over 单独承担。

### R13 — [minor] `CheckOrigin` 恒真：生产同样接受跨站 WS（CSWSH 面）

- **位置**：`backend/internal/ws/server.go:43`
- **描述**：凭证不走 cookie（token 在应用层 hello），跨站劫持拿不到凭据，影响面主要是"任意站点可匿名开游客连接"。但生产单端口同源部署下收紧 Origin 零成本。
- **修复建议**：默认校验 `Origin` host == `r.Host`，env 开关放行 dev。

### R14 — [minor] 掉线期/重连期客户端仍可点格，move 静默吞没

- **位置**：`frontend/src/pages/Game.tsx:130-150`（`playable = cell===0 && myTurn`，不看 `session.status`）；`frontend/src/ws/client.ts:98-104`（`send` 返回 false 无回执）
- **描述**：连接断开后旧 `game` 仍在，`myTurn` 为真 → 格子可点 → `ws.send` 因 readyState 非 OPEN 返回 false → 动作丢���无提示。用户以为落子成功，其实回合钟在服务端继续走。
- **修复建议**：`playable` 加 `session.status==='connected'`；`api.move`/`send` 失败时给 error toast。

### R15 — [minor] 双方同时断线时"先断者判负"：规则属 spec 灰区，但行为突兀

- **位置**：`backend/internal/game/actor.go:274-290`
- **描述**：两人都掉线时 `onReconTimeout` 取**最早过期**的 `reconAt` 判负——先断线者负，哪怕对方同样始终未归。protocol §5"窗口到期未回：断线方判负"字面可辩护，但双断场景下"谁先掉线谁输"对玩家不合理（后掉线者甚至没机会"先到"），且不在测试覆盖内。
- **修复建议**：冻结契约可解释为现状合规；更合理是双方都离线时延后到任一方重连再判，或判 draw——建议记入 DECISIONS 明确取舍（修规则需动 PROTOCOL.md）。

## 其余小项（不计入正式清单）

- `go.mod:5` gorilla 被标 `// indirect` 实为直接依赖，`go mod tidy` 修正。
- 慢消费踢除路径在 close 前会把 64 帧 backlog 全量 flush（`conn.go:76-91`），坏 conn 时首写吃满 `WriteWait=10s` 才关 —— 延迟可接受但与"踢出"语义略拧。
- `h.Metrics().lobbyPlayers` 含 StateWaiting（`hub.go:116`），与"lobby 玩家"口径可商榷。
- resume 改 nick → `UpdateNick` 只改会话记录，进行中对局的 `Seat.Nick` 快照不变（`handlers.go:81-83`/`hub.go:352-355`），房间内昵称可漂移。
- e2e 未覆盖：busy-token/unauthorized、广播风暴踢人、stale-state 重连、双断窗口 —— 建议补（R1/R2/R3/R15 对应回归测试）。

## 结论

M1 骨架（actor 邮箱模型、锁序、协议字段）质量不错，`go test -race` 全绿；问题集中在**重连生命周期的边角**（R1/R2）、**广播背压**（R3）与**会话/actor 资源回收**（R4/R5）。R1 建议优先修——它直接破坏"断线重连"这一 M1 招牌流程的真实使用场景。
