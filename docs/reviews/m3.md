# REVIEW_M3 — gomoku-battle M3 阶段独立评审

基点：`origin/main` @ `a641d37`（相对 `m2-done` tag）。只读评审，未改代码。
验证：`go test -race ./...` 全绿；本地起 `gserver`(DefaultConfig)+ `loadtest` 实测 10 房×40s/60s；对全部 `docs/evidence/bench-*` JSON 逐项对账 BENCHMARK.md；对压测进程取 SIGQUIT goroutine dump 取证。

**一句话结论**：RoomListFlush 本身并发正确（dirty 合并=h.mu 串行化、快照是全量列表故最终一致），但 **loadtest 工具存在三类系统性测量缺陷**——连接全部在 hello+30s 被服务端踢死、配对复用逻辑被自身泄漏的读帧 goroutine 抢帧、lastMove 匹配会"假接收"。所有已发布的 60s 档位数据实际上只包含 ~30s 真实负载 + ~30s 死尾，BENCHMARK.md 的表格另有与证据文件不符的数字。

---

## major

### M3-R1 压测连接全部在 hello+30s 被服务端批量踢死 —「60s 档」实为 ~30s 负载
- **位置**：`backend/cmd/loadtest/main.go:178` `wsclient.DialOpts(*addr, nil, true)`；`backend/internal/wsclient/client.go:56-58`（suppressPong 装 `SetPingHandler(func(string) error { return nil })`）；服务端 `backend/internal/ws/server.go:192`（hello 后 `SetReadDeadline(now+WSPongWait=30s)`，仅 pong 续期）。
- **问题**：suppressPong 是 e2e 测试用来验证 pong 超时的探针选项，压测误用 → 每条连接 hello 后 30s 必被服务端 read-deadline 踢掉，与本端是否发 ping 无关（gorilla 的 read deadline 是绝对时刻）。
- **实证**：本机 10 房×40s：hello≈21:41:28 → connections 20→0 于 21:41:59（≈31s）。证据文件同构：bench-200 conns 400→0 于 21:33:28-29（hello≈21:32:58）；bench-500-after 1000→0 于 21:30:56-57（≈hello+30s）；bench-500-before 与 bench-1000 同样在满编后 ~30s 处清零。
- **影响**：每个 60s 档仅前 ~30s 是真实负载，后 ~30s 服务端连接数为零、对局靠 turn 超时收尾；`moves_per_s`、`games_finished`、`duration_s` 均含死尾。
- **修复**：loadtest 拨号改 `DialOpts(*addr, nil, false)`（或默认 `Dial`），保留 suppressPong 仅供超时测试。

### M3-R2 pairRun 读帧 goroutine 泄漏 + 跨迭代偷帧 — 再配对必然饥饿，压测进程卡死到 deadline
- **位置**：`runpair.go:30-64`（每次 pairRun 为每条 conn 起一个 forwarder，仅当 `c.Read` 出错才退出）；`main.go:217-237`（外层用裸 `p.a.Read(5s)` 读 room{created}，与残留 forwarder 竞争同一 `c.incoming`）。
- **问题**：pairRun 返回后 forwarder 不退出（无 done/ctx），继续读 conn 的 incoming 队列并把帧塞进无人消费的 `ch`。下一轮 create/join 握手时，`p.a.Read` 与僵尸 forwarder 抢同一队列——room{created}/game_start/甚至断开连接的 `{err}` 都可能被偷走 → `a.Read` 5s 超时（`read_room_created`）或空转到 deadline。
- **实证**：10 房×40s：`games_started=11`（10 对基本各只打了 1 局）、`read_room_created=9`；SIGQUIT dump：多个 pair goroutine 栈停在 `pairRun`→`nextFrame`(`runpair.go:94`)，其 forwarder 栈停在 `Client.Read`→`readIncoming`(`client.go:121`) 空等——pump 已全部退出、incoming 空、{err} 被另一读端偷走 → pair 与 forwarder 互锁到期。`duration_s==40.005/60.005` 精确等于 deadline 即由此造成。bench-200 里 `read_room_created:187 ≈ 216 started` 亦完全吻合「每对第二局必败于偷帧」。
- **后果**：benchmark 宣称的「持续 60s 负载」不成立——实际每对≈1 局后瘫痪；还泄漏 goroutine（每次 pairRun 2 条/conn）。conn 死亡时僵尸 forwarder 还可抢 `{err}` 使其他读端 90s 才发现。
- **修复**：forwarder 加 `done chan struct{}`（pairRun defer close）；room{created} 等待走与 pairRun 相同的 frames 通道或显式忽略非匹配帧；或在 pairRun 返回前显式 `a.Read(0)` 排空并停掉转发器。

### M3-R3 lastMove 匹配法的「假接收」：随机落子撞上对手旧手同格 → 计虚假延迟样本 + 级联 not_your_turn
- **位置**：`runpair.go:87-112`：`x,y := rand.Intn(15), rand.Intn(15)`；accepted 判定为「第一个 lastMove==(x,y) 的 game_state」。
- **问题**：随机的 (x,y) 不查占用 → 与**对手此前某一手**同格的概率随棋盘中盘显著上升（bench-200 `illegal_move=5463`/`moves_total=16030`，发送侧约 1/3 非法）。命中路径：对方更早落在 (x,y) → 我方随机再发 (x,y) → 先到的是对方那条 lastMove=(x,y) 的 game_state → 判定「accepted」、计入延迟样本、swap mover → 我方真正的 illegal_move 帧随后到达 → `goto retry` 在**对方回合**发子 → 报 `not_your_turn`、pairRun 直接 return。
- **实证**：bench-200 `not_your_turn:82`、bench-500-before `190`、bench-1000 `248`——在严格交替协议下不该出现；BENCHMARK.md §2 把 not_your_turn 归为「预期协议行为」**结论错误**：这是工具自身的回合失同步，且意味着部分延迟样本测量的是**别的广播**（样本被污染+真实样本丢失同时发生）。
- **修复**：accepted 判定加 turn 校验（game_state 需同时满足 lastMove==(x,y) 且 `turn==对手色`）；发子前在本地棋盘查占用即可消除非法重试洪泛；not_your_turn 应单列为「工具失同步」而非「预期」。

### M3-R4 掉帧幸存者偏差 + 吞吐/完成率口径错 — p99/max 与 moves/s 系统性失真
- **位置**：`runpair.go:56-61`（ch cap=256，`default:` 分支**驱逐最旧帧**再塞新帧）；`main.go:264-272`（`moves_per_s = moves/elapsed`，`games_started/finished` 由 pairRun 启动/退出计数）。
- **问题**：(a) 压测尖峰期 accept 帧被驱逐 → 该手在 `nextFrame` 空等到 deadline——**最慢的样本恰好被丢出分位数统计**，p95/p99/max 偏低（经典幸存者偏差）；game_over 同样可被驱逐。(b) `moves_per_s` 用 `elapsed`（=60.005 含 ~30s 死尾）分母，吞吐被低估约 2×。(c) `games_started` 实际是「pairRun 启动次数」（create/join 失败已提前 return 不计，但 `started++` 在 pairRun 前），`games_finished` 是「pairRun 任意路径退出次数」——bench 四档 finished 恒等于 started，恒真等式本身证明它不度量「完成的局数」。
- **修复**：accept/终局帧独立计数（moves_sent vs moves_accepted）；吞吐按「真实有载窗口」（首 conns>0 → 末 conns>0）计；evict 事件计数进 errors；finished 仅统计收到 game_over 的局。

## minor

- **M3-R5** `pollMetrics` 数据竞争：`main.go:116` `*out = append(*out, s)` 由轮询 goroutine 写，`main.go:271` 最终 marshal 时主 goroutine 读 `samples`——close(stop) 后无同步，slice header 读写竞态（-race 可检出；极端时 len 超 cap 或 marshal 崩）。另 `resp.Body` decode 错误被吞 → 追加零值样本。修：poller 退出后再 close(stop)+join，或 samples 加 mutex。
- **M3-R6** 配对握手静默吞错误帧：`main.go:217-228` `p.a.Read` 循环只认 `room{created}`，`error`(already_in_room)、`room_list`、对局残留帧全部丢弃不计——失败原因被统一误记为 `read_room_created`。修：循环内对 `type=="error"` 计 `errs.add(code)`。
- **M3-R7** BENCHMARK.md 与证据不符：§2 表 200 房「连接建立 0.23/2.2/9.5」实为 move 延迟数（证据 connect_ms 是 0.207/0.58/4.19）；500/1000 档 connect 列写「—」但证据有数据且很糟（500-before p95=553.6ms、p99=939.2ms；1000 档 p95=1548ms、p99=3529ms）——**1000 档连接建立劣化被选择性略去**，影响「不塌点」结论的完整性。
- **M3-R8** 数据不自洽：bench-1000 `conns_dialed=1999` 但 errors 无 `dial` 项（应有 1 次失败记录或对 2000 口径说明）；`hellos=1998` vs `hello:1` 能对上但 dialed 对不上。另 `gamesPlayed` 服务端计数跨 run 累积（bench-200 首样本已 3288），BENCHMARK 未声明基线清零，「完成局数」列与 server 侧增量无对照。
- **M3-R9** wsclient.Client：(a) `pump` 向 cap=256 的 `incoming` 阻塞投递（client.go:69-77），消费端停滞时泵死、断连 `{err}` 无法投递——压测端自身成为「慢消费」来源并把断连静默化；(b) `Send` 无写锁，pairRun 单写者才侥幸安全（runpair.go:89 仅 pair goroutine 发），cmd/wsclient 若加并发写会撕包。
- **M3-R10** `broadcastRoomList` Flush=0 同步路径仍写 `h.rlDirty=true` 死位（hub.go:241-247）；且合并只是降频——`roomListMsgLocked` 仍在 `h.mu` 下 O(rooms) 渲染（hub.go:259-264），flusher 每次 tick 仍持锁渲染+取 lobby conns 快照。正确性 OK，但对「锁内序列化+渲染成本」的瓶颈语义未变，p99 尾部（942.6ms 反而劣于 before 的 682.6ms）也印证写阻塞仍在 conn 层。
- **M3-R11** `nextFrame` 每调用 `time.After(time.Until(deadline))` 分配一次分钟级定时器（runpair.go:167）；`latency` 全量切片驻留（main.go:43-53，O(moves) 内存，长档位 GB 级趋势）；`cpuRSS` 硬编码 USER_HZ=100（main.go:127）与 `VmRSS` sscanf 脆弱；`http.Get` 无超时（main.go:108），/metrics 挂起则 poller 永久阻塞。
- **M3-R12** `connect_ms` 只测 TCP+WS 握手（DialOpts 返回即止，main.go:177-185），hello 时延未计——BENCHMARK 表写作「连接建立」与代码一致但与「端到端可用连接」语义有差；`games_finished`/`started` 命名同上 R4。
- **M3-R13** 证据卫生：`docs/evidence/pprof-*-heap.pb.gz`、cpu.pb.gz 为二进制 blob 直接入仓（9–21KB），无对应文本 top；`bench-sanity-20r.json` 与其余 .txt 命名不统一（JSON 存成 .txt 也易误导）。
- **M3-R14** `actor_test.go` flake 修复（`cap.frames[white][base:]` 切片基线）思路正确，但 base 采样点在 `Reconnect` 之前 —— 若两事件间有 in-flight presence 仍会漏判；当前用例时序上安全，作为 pattern 易被误拷到并发更高的断言场景。建议封装 `framesSince(key, mark)` 帮助函数。
